# Doctor-Wang 完整实施计划

更新日期：2026-10-17

## 1. 产品定位

Doctor-Wang 的最终形态是一个面向个人用户的健康档案与 AI 健康辅助产品。它帮助用户整理检查报告、理解已有医疗信息、记录健康档案，并在明确的医疗安全边界内进行健康咨询和焦虑缓解。

产品不提供确定性诊断、处方、停药或剂量调整，也不替代医生、急诊服务或心理危机干预。

## 2. 最终实现目标

最终系统应具备以下闭环：

- 用户通过正式签名的 Android 应用安全注册、登录和管理账号；
- 用户上传 PDF 或图片报告，系统完成文件安全校验、OCR、结构化解读、向量化和可追溯存储；
- AI 问诊只使用当前用户获授权的健康档案与报告证据，并返回引用、风险等级、警告和 trace ID；
- 安心话聊能够区分客观证据与健康焦虑，在高风险或证据不足时升级处理而不是生成安抚性结论；
- 后端统一承担认证、授权、用户隔离、审计和业务事实，客户端不直接调用模型供应商；
- AI Service 在模型、OCR、向量库或证据不可用时 fail closed；
- 生产环境具备受信任证书、备份恢复、监控告警、资源保护、漏洞处置和可回滚发布；
- 每次发布均由自动化测试、医疗安全评测、真机验收和生产 smoke 共同放行。

### 最终完成判定

只有同时满足以下条件，项目才能宣称达到正式可用状态：

1. 域名、ICP 备案和受信任 HTTPS 证书完成，客户端不依赖 IP 或自签证书；
2. Android release 包使用受保护的正式签名并完成升级、回滚和安装验证；
3. 报告上传、解析、问诊、安心话聊、档案、改密、登出和注销在真机上全流程通过；
4. 高风险症状、证据不足、提示注入、跨用户访问和 provider 故障测试全部通过；
5. 文件扫描或经批准的等效风险控制在生产环境启用；
6. 数据库、报告文件和配置能够从备份在目标恢复时间内恢复；
7. 监控覆盖可用性、错误率、延迟、队列、资源、AI 失败和备份状态，并能送达值班人员；
8. 数据保留、账号注销、审计、隐私说明和用户同意流程有可验证实现；
9. 发布清单、运维手册和项目状态与实际部署一致。

## 3. 非目标与边界

- 不建立在线诊断、处方或药品推荐能力。
- 不让模型或 Agent 决定用户权限、报告归属或高风险分流规则。
- 不在 Android 客户端保存 provider 密钥或直接访问 provider。
- 不把 mock、内存向量库、SQLite job state 或自签证书描述为生产完成。
- 不在没有真实证据和人工复核路径时扩展到医生端、医院端或多机构协作。
- 不以新增功能数量代替安全、隐私、可恢复性和真机可用性验证。

## 4. 当前基线

当前代码已经覆盖 Android、Spring Boot、FastAPI/LangGraph、PostgreSQL/pgvector 和 Docker Compose 完整链路，并包含认证、报告、健康档案、问诊、安心话聊、报告解读、引用、安全门、审计和 AgentOps-J 可选网关。

已有记录显示本地测试、CI、生产部署和真实 provider 链路曾经通过，但其中部分证据来自 2026 年 8 月。下一轮工作必须重新验证当前服务器、证书、备份、APK、provider 和监控状态，不能把历史通过自动视为当前通过。

## 5. 目标架构

```text
Android App
    |
    | HTTPS + JWT session
    v
Spring Boot API
    |-- Authentication / authorization / user isolation
    |-- Health profile and report business state
    |-- File validation, lifecycle, audit, idempotency
    |-- Chat safety context and trace correlation
    |
    +--> PostgreSQL + pgvector
    +--> Object/file storage + malware scanning
    +--> FastAPI / LangGraph AI Service
             |-- OCR provider
             |-- Embedding provider
             |-- LLM provider or AgentOps-J gateway
             |-- Evidence retrieval and safety gate
             +-- Evaluation and audit metadata
```

任何跨边界变更都必须保留 `Android -> Spring Boot -> AI Service -> Provider` 调用链。生产业务事实以 Spring Boot 和 PostgreSQL 为准，AI Service 只处理已授权上下文。

## 6. 分阶段实施路线

### M0：现状再基线化

目标：确认 2026-10-17 的代码、部署与文档真实状态。

- 在干净环境运行 Android、后端和 AI 全量测试及构建。
- 在 Docker 环境补跑 PostgreSQL/Testcontainers、Compose、Nginx 和服务间契约测试。
- 检查生产服务器健康、资源、镜像版本、数据库 migration、定时任务和备份文件。
- 对照 README、roadmap、`.ai/state/`、API 文档和当前实现，消除测试数字与状态漂移。
- 建立 release candidate 版本号、变更记录和可回滚基线。

退出门槛：所有检查都有日期、命令、版本和结果；未运行项明确标记 `NOT RUN`，生产状态不再依赖历史推断。

### M1：Android 真机与可访问性验收

目标：证明核心用户旅程在真实设备上可用。

- 覆盖登录、注册、报告上传、状态轮询、解读、下载、删除、重试、问诊、安心话聊、档案、改密、登出和注销。
- 在 375/390/430dp 等效宽度检查小屏、横竖屏、键盘遮挡和长文本。
- 验证暗色模式、动态字体、TalkBack、触控目标和错误焦点。
- 覆盖断网、慢网、超时、401、429、5xx、上传中断和应用重启恢复。
- 修复 ReportList/ProfileEdit 的统一会话失效导航等已记录 P3 项。

退出门槛：验收清单全部有真机证据；无 P0/P1 缺陷，P2/P3 有明确处置结论。

### M2：正式发布链路

目标：从调试部署升级为可验证、可回滚的正式发布。

- 完成域名、ICP 备案、DNS 和 Let's Encrypt 或等效受信任证书。
- 移除客户端对裸 IP 和自签证书的生产依赖。
- 建立 Android keystore 托管、release 签名、版本号和升级策略。
- 增加 staging 环境以及 production 配置差异检查。
- 发布前自动验证镜像、migration、配置、APK 和下载渠道。
- 定义回滚步骤，包括应用、后端、AI 服务和数据库兼容性。

退出门槛：新设备可通过正式 HTTPS 安装并完成核心流程；一次演练能在规定时间内回滚。

### M3：文件与数据安全生产化

目标：关闭上传、存储和删除生命周期的剩余风险。

- 根据资源评估选择升级到 4GB 以上并启用 ClamAV，或接入隔离的扫描服务。
- 在扫描不可用、超时或结果不确定时保持 fail closed。
- 完成 MIME、magic number、大小、压缩炸弹、重复文件和恶意文件测试。
- 将报告原文件迁移到受控对象存储，采用短期签名访问和服务端授权。
- 验证注销、报告删除、失败任务和过期对象的级联清理。
- 建立数据保留、导出、删除和审计政策。

退出门槛：上传安全和对象生命周期有生产配置、自动化测试及审计证据。

### M4：AI 安全与质量门禁

目标：让 AI 行为可评测、可解释、可阻断。

- 将评测集按报告解读、一般咨询、安心话聊、高风险、拒答、提示注入和引用正确性分层。
- 固定 parser、prompt、model、retrieval 和 safety 版本元数据。
- 增加 OCR 低置信、矛盾报告、过期证据、跨 namespace 和 provider 故障用例。
- 为忠实度、证据覆盖、引用有效性、拒答正确率和高风险召回设置 release 阈值。
- 把 AgentOps-J 网关纳入相同评测，证明经过网关不丢失 system prompt 和安全参数。
- 为必须人工复核的结果提供明确状态和用户文案。

退出门槛：任何低于安全阈值的版本无法发布；结果可追溯到输入证据和组件版本。

### M5：可观测性、备份与恢复

目标：发现故障并从故障中恢复。

- 监控 HTTPS、后端、AI、PostgreSQL、pgvector、队列、磁盘、内存、swap 和备份。
- 建立错误率、延迟、provider 故障、任务积压、扫描失败和资源水位告警。
- 将 trace ID 贯穿 Android、后端、AI Service 和 AgentOps-J，且不记录健康原文。
- 对数据库和报告文件执行自动备份、异地复制、加密和保留策略。
- 每季度执行一次恢复演练，验证 RPO/RTO 和报告文件一致性。
- 形成 OOM、provider 故障、数据库异常、证书到期和疑似泄露 runbook。

退出门槛：告警可送达、恢复演练成功、备份不可用能被主动发现。

### M6：稳定运营与受控演进

目标：在安全基线稳定后扩展产品价值。

- 通过脱敏反馈和埋点识别报告解读与安心话聊的真实失败模式。
- 增加用户可理解的引用定位、历史趋势和报告对比，但不生成确定性诊断。
- 在明确租户模型后再评估家庭共享或多用户协作。
- 建立依赖升级、漏洞响应、密钥轮换和模型变更流程。
- 定期归档 `.ai` 已完成任务，保持状态文件简洁且可信。

退出门槛：新增能力有用户价值证据，不降低既有医疗安全、隐私和可恢复性指标。

## 7. 测试与发布门禁

每个垂直切片至少验证：

- 正常流程、边界输入、空数据、重复请求、超时、断网和重试；
- 未登录、过期 token、撤销 token、跨用户访问和权限绕过；
- 高风险症状、无证据、提示注入、引用错误和 provider 故障；
- migration 前后兼容、客户端契约和回滚路径；
- 日志、trace、错误响应和测试夹具不包含真实健康数据或密钥。

发布结论只允许：

- `ACCEPT`：全部阻断门禁通过；
- `REWORK`：实现存在可修复缺口；
- `BLOCK`：安全、隐私、契约、恢复或环境证据缺失。

## 8. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 历史部署证据已过期 | 每个 release candidate 重新生成带日期证据 |
| 低内存服务器再次 OOM | 容器限制、资源告警、容量测试和升级门槛 |
| AI 生成无证据结论 | 引用校验、fail closed、评测阈值和人工复核 |
| 健康数据泄露 | 最小授权、用户隔离、脱敏、保留策略和审计 |
| 文件上传恶意内容 | 隔离、扫描、类型校验和对象生命周期控制 |
| 客户端与 API 漂移 | 契约测试、兼容窗口和分阶段发布 |
| provider 或网关故障 | 超时、熔断、明确不可用提示和回滚直连 |

## 9. 推荐执行顺序

1. 先完成 M0，取得可信的当前基线。
2. M1 与 M2 形成用户可安装、可验收的正式发布链路。
3. M3、M4、M5 完成生产安全、AI 质量和运维闭环。
4. 只有前述门禁稳定后才进入 M6 的功能演进。

短期优先级不是继续增加页面，而是完成真机、正式证书、签名发布、文件安全、告警和恢复演练。
